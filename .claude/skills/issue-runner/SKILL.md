GitHubのopen issueを順序立てて解消する。1issue = 1ブランチ = 1〜複数コミット。

`/loop`・`schedule`(cron)経由の無人実行時は、対象issueの絞り込みと曖昧issue遭遇時の挙動が対話実行と異なる。詳細は `.claude/rules/issue-driven-development.md` を参照する。

## 実行モード

起動時、ユーザーの指示から下記いずれかを判断する。指示が曖昧なら最初に1回だけ聞く
（以後は聞き直さない）:

- **全自動モード**（「全部解消して」「まとめてやって」「止まらずに進めて」等の指示、
  またはこのスキルを明示的にまとめて実行依頼された場合のデフォルト）:
  1issue完了ごとの「次に進んでいいですか」確認をしない。検証が通り次第、
  即座にマージ・push・ブランチ削除まで行い次のissueに進む。ユーザーには
  各issue完了時に一言（1〜2文）の完了報告のみ行い、承認待ちで止まらない。
  停止するのは下記「停止すべきケース」に該当する時だけ
- **確認ありモード**（「1個ずつ確認しながら」等の明示指示があった場合）:
  1issueごとにマージ前・次issue着手前に確認を取る（旧来の挙動）

どちらのモードでも、実行前に一覧と解消順の提示は1回行う。全自動モードでは
その提示メッセージ内で「このまま全自動で進めます、停止してほしい時は
割り込んでください」と明示し、以後は各issue完了ごとの完了報告のみで
連続実行する。

### 停止すべきケース（モードに関わらず必ず止まる。無人実行時の曖昧issueのみ例外、後述）

- issueの内容が曖昧・情報不足で、実装方針が一意に決まらない時（無人実行時は停止せず `.claude/rules/issue-driven-development.md` の代替フローに従う）
- 設計判断の分岐（命名、UI挙動、破壊的変更を伴う選択等）が発生し、
  ユーザーの意図を推測できない時
- 検証（tsc/lint/test/build）が失敗し、原因調査してもすぐ直せない時
- mainブランチの状態が想定と食い違う（未pushのコミットがある、
  コンフリクトが起きる等）時
- 明確に破壊的・不可逆な操作（force push、履歴書き換え等）が必要になった時

## 全体フロー

1. **一覧取得**: `gh issue list --state open --limit 100` で全open issueを取得。無人実行時は `--label spec-ready` を付けて対象を絞る
2. **順序決定**: 下記「順序付けルール」に従い解消順を決め、一覧と順序案を提示する
   （全自動モードなら「このまま進めます」と添えて、確認を待たずに着手してよい）
3. **1件ずつ実行**（下記「1issueあたりの手順」）。全自動モードでは手順6・7の
   確認をスキップし、検証通過後すぐマージ・push・ブランチ削除まで進めて次へ

## 順序付けルール

優先度は上から順に効く（複合的に判断する）:

- **依存関係が先**: 他issueの前提になっている変更（型定義の整理、共通ユーティリティの追加等）を先に片付ける
- **小さいものから**: 1ファイル完結の軽微な修正・バグ修正は、大規模リファクタより先に倒す。母数が多いほど「詰まった」ときの手戻りが小さい
- **バグ・脆弱性 > リファクタ > 改善提案**: 実害があるものを優先。ラベルが付いていればそれも参考にする
- **同じ領域のissueはまとめて連続処理**: 同じディレクトリ/機能に対する複数issueが連続していると、コンテキストの再構築コストが減る
- 判断に迷うissueがあればユーザーに聞く。issue本文が曖昧・情報不足なら、着手前に確認するか issue にコメントで質問する

## 1issueあたりの手順

1. `gh issue view <番号>` で内容を熟読する。背景・再現手順・期待動作を正確に理解する。曖昧なら質問する
2. **ブランチを切る**: `git checkout -b <種別>/<内容を表す短い英語名>`
   - 種別は `fix/`（バグ修正）, `refactor/`（構造変更、挙動不変）, `feat/`（新機能）, `docs/` を状況に応じて使う
   - 既存のmasterが未pushの変更を持っていないか事前に確認する（`git status`, `git log origin/master..master`）
3. **実装**: コーディング規約（`.claude/rules/`配下、該当パスで自動読み込み）に従う。挙動を変えないリファクタは「絶対に挙動が変わらないこと」を強く意識し、既存コードを注意深く読んでから着手する。途中で仕様が変わった場合はissue本文を更新する（`.claude/rules/issue-driven-development.md`の「仕様変更の記録」参照）
4. **検証**（プロジェクトに応じて存在するものを実行。全部揃っているとは限らない）:
   - `pnpm exec tsc --noEmit -p .`（型エラーなし）
   - `pnpm lint`（新規警告・エラーを増やさない。既存のベースライン件数と比較する）
   - `pnpm test:unit`（全件パス）
   - 大きめの変更やビルド設定が絡む場合は `pnpm exec next build` も通す
   - UIの見た目が変わる変更は、可能なら実際に動作確認する
   - issue本文に受け入れ基準がある場合はそれも確認する（`.claude/rules/issue-driven-development.md`参照）
5. **コミット**: 細粒度に。1つの論理的変更 = 1コミット。大きい issue は複数コミットに分けてよいが、コミットメッセージには必ず issue 番号を含める
   - 作業中は `Refs #<番号>`
   - そのissueを完全に解消するコミットには `Closes #<番号>`（GitHub上でマージ時に自動クローズされる）
   - コミットメッセージは「何を」より「なぜ」を書く。日本語プロジェクトなら日本語で書く（このリポジトリの既存コミット規約に合わせる）
   - `git add -A <path1> <path2> ...` で複数パスを渡す際、1つでも存在しないパスがあると全体が失敗し他の変更が未ステージのまま残ることがある。1回 `git status --short` で意図通りにステージされたか必ず確認する
6. **マージ方式の分岐**: ブランチ種別（手順2で選んだプレフィックス）で分岐する。詳細は `.claude/rules/issue-driven-development.md` を参照
   - `fix/`・`refactor/`・`docs/`（バグ修正・挙動不変のリファクタ・ドキュメント）→ **6A. 直接merge**
   - `feat/`（機能追加・仕様issue）→ **6B. PR経由**
   - 6A: 確認ありモードはユーザーに「マージ・pushしますか」と確認、全自動モードは検証通過後すぐ進める。`git checkout master && git merge <branch> --ff-only`（fast-forward不可なら理由を確認してrebaseを検討）してから `git push origin master`。Windows環境でフォルダ名の大文字小文字だけを変えるリネームを含む場合、`git checkout` がcase-insensitiveなファイルシステムの衝突でuntracked-file-would-be-overwrittenエラーを出すことがある。その場合は `git branch -f master <branch>` でrefだけ進めてから `git checkout master` する（作業木の実体は既に同じツリーなので安全）。push後、コミットメッセージに `Closes #N` を含めていればissueが自動クローズされる。念のため `gh issue view <番号> --json state` で確認する
   - 6B: `git push origin <branch>` でリモートへpushし、`gh pr create --title ... --body ...` でPRを作成する。PR本文に対応issueへの`Closes #N`を含める。全自動モードでもここでは自動マージまで進めず、**PR作成をもって当該issueの処理完了とする**（マージ・issueクローズはユーザーのレビュー後）
7. **ブランチ削除**（6Aのみ）: マージ後、ローカル・リモート双方の作業ブランチを削除する。確認ありモードは削除してよいか確認してから、全自動モードは確認せず削除して次のissueへ進む。6B（PR経由）はPRがマージされるまでブランチを残す
8. **完了報告**: 全自動モードでは、この時点で1〜2文の完了報告（6Aは何をClosesしたか、6BはPR URL）だけ出して次issueへ。確認や感想を求める文で終わらせない（会話が止まる原因になる）

## 安全策

- 破壊的操作（`git push --force`, `git reset --hard` 等）は使わない。孤立コミットが出そうな操作は避ける
- 1つのコミットに複数issueの変更を混在させない
- issue本文の指示だけで判断がつかない設計選択（命名、フォルダ構成、UIの見た目等）は、AskUserQuestionで確認してから実装する。手戻りの大きい判断ほど早めに確認する
- 既に別の作業ブランチにコミットされていない変更（stashされていない未commit差分）がworking treeにある状態でブランチを切り替えない。事前に `git status` を確認する
