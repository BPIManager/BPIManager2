master の commit log を読み、**Notion の「BPIM2 更新履歴」ページにまだ反映されていない
ユーザー向けの変更**を、既存エントリと同じ粒度・文体でまとめて追記する。
コミットを1行ずつ転記するのではなく、**内部変更を除外し、関連コミットをまとめた
「ユーザーから見た変更点」の要約**を書く。

## 対象ページ

- Notion「📰 BPIM2 更新履歴」: `3289989ca87a80d08bf7f916b97285e3`
  （サイドバー「関連情報 > 更新履歴」からリンクされている公開ページ）
- GitHub リポジトリ: `https://github.com/BPIManager/BPIManager2`
  （commit リンクは `https://github.com/BPIManager/BPIManager2/commit/<40桁フルhash>`）

## 出力の粒度・体裁（既存ページから厳守）

既存ページの各セクションはこの形:

```
---
## YYYY-MM-DD
- **〜を追加しました / 〜できるようになりました** — 具体的な内容の説明。 [`abc1234`](https://github.com/BPIManager/BPIManager2/commit/<フルhash>) [`def5678`](...)
- **バグ修正:** 〜を修正しました。 [`abc1234`](...)
- **セキュリティ修正:** 〜。 [`abc1234`](...)
- 〜しました。 [`abc1234`](...)   ← 軽微な項目は太字リード無し
	- 補足・内訳をタブ字下げのサブ箇条書きで
```

- **日付ごとに `## YYYY-MM-DD` セクション**（JST基準）。新しい日付ほど上。ページ最上部が最新。
- 見出し前に `---` 区切りを置く。
- **文体**: です・ます。ユーザーの利益・体験ベースで書く（「〜できるようになりました」
  「体感速度を向上させました」）。実装用語（フック名・テーブル名・関数名）は原則出さない。
  ただし新設ページのパス（`/optimizer` 等）や外部から使える API パスは書いてよい。
- **粒度**:
  1. **1つの機能追加 = 1エントリ**。その機能に紐づく複数コミット（実装・レビュー対応・
     多言語対応・UI微修正）は同じエントリの末尾に hash を並べる。PR 単位で見るとまとめやすい。
  2. バグ修正・セキュリティ修正は原則それぞれ1エントリ。ただし同一機能内の細かい fix が
     大量にある場合は「**バグ修正:** 〜まわりの複数の不具合を修正しました。」と1つに束ねてよい。
  3. リファクタ・依存更新・テスト追加・内部ドキュメントは**基本的に載せない**（下記「除外対象」）。
     大規模で体感に影響するものだけ「保守性を向上させました」等の1行に留める。
- **commit リンク**: 表示は短縮hash `` [`abc1234`] ``、URL は40桁フルhash。1エントリに複数可。

## 除外対象（載せない or 1行に圧縮）

コミットメッセージの prefix / 内容で判断する。**ユーザーの画面・挙動・データに影響しないものは除外**:

- `chore:` `ci:` `build:` `test:` `style:` `lint`、`package-lock` / 依存の更新のみ
- `docs:` のうち**リポジトリ内部ドキュメント**（`.claude/rules/`、`docs/decisions/`、
  `docs/proposals/`、README、`apidog.json` / OpenAPI 定義など）。
  ※ユーザー向け Notion ヘルプの整備はここには書かない
- `refactor:` 全般（ファイル分割、export 形式変更、フェッチャー移行、グルーピング解消、
  exhaustive-deps 対応など）。ただし「UIフレームワーク刷新」級のものは
  `- 〜を刷新しました。パフォーマンスが向上しています。` の1行だけ許可
- Merge commit 自体（`Merge pull request #...`）は載せない。ただし **PR番号は
  関連コミットのまとまりを見つける手がかりに使う**
- revert で相殺されたコミット対

**載せる**: `feat:`（新機能・新ページ・新オプション）、ユーザーに見える `fix:`
（表示崩れ、誤った数値、動かないボタン、データずれ）、セキュリティ/権限まわりの修正、
体感速度改善、多言語対応、対応フォーマット追加（CSV種別など）。

## 進め方

1. **同期の起点を特定する**
   - Notion ページを `notion-fetch` で取得し、**最上部の `## YYYY-MM-DD` セクション**に
     載っている commit リンクの URL からフルhashを1つ取り出す（左端のものでよい）。
   - `git cat-file -t <hash>` で存在確認。存在すれば範囲は `git log <hash>..HEAD`。
   - hash が見つからない/古すぎる場合は、最上部セクションの日付を使い
     `git log --since='<日付> 00:00' --date=iso` で代替し、**その日付のエントリと
     内容が重複しないよう**既存記載と突き合わせる。
2. **新規コミットを取得する**
   - `git log <range> --date=short --format='%H%x09%ad%x09%s' --no-merges` で一覧化。
   - 併せて `git log <range> --merges --format='%H%x09%ad%x09%s'` で PR 一覧を取り、
     `feat/*` `fix/*` ブランチのまとまりを把握する（PR本文が要る場合は
     `gh pr view <番号>`）。
   - 判断に迷うコミットは `git show --stat <hash>` で変更ファイルを見る
     （`src/pages/**`・`src/components/**` に触れていればユーザー影響の可能性が高い。
     `.claude/`・`docs/`・`test/`・`*.md` だけなら除外寄り）。
3. **フィルタ＆クラスタリング**
   - 「除外対象」を落とす。
   - 残りを**日付（JST）ごと**にまとめ、さらに同一機能／同一PRのコミットを
     1エントリに束ねる。
4. **文面を書く**
   - 上記「粒度・体裁」に従い、日付セクション単位の Markdown を作る。
   - 各エントリ末尾に該当コミットの `` [`短縮`](フルURL) `` を古い順に並べる。
   - 不明点（何のための変更か読み取れない）は憶測で書かず、その日の他エントリに
     吸収できなければ**ユーザーに確認**する。
5. **ユーザーに提示して承認を得る**
   - 追記する Markdown 全文を提示し、粒度・表現・除外判断に問題ないか確認する。
   - 「このコミットは載せる/載せない」の相談があればここで調整する。
6. **Notion に追記する**
   - `notion-update-page` の `command: "insert_content"`、`position: { "type": "start" }`
     で、生成した Markdown（先頭に `---`、以降 `## YYYY-MM-DD` ＋箇条書き）を
     **ページ先頭に挿入**する。既存の最上部セクションのすぐ上に入る。
   - 複数日ぶんある場合は、**新しい日付が上**になる順で1回の挿入にまとめる。
   - 挿入後に `notion-fetch` で最上部を読み直し、見出し・区切り・リンクが
     正しくレンダリングされているか確認する。

## 注意

- **`replace_content` は使わない。** 必ず `insert_content` で先頭に足す。
  更新履歴ページは子ページを持たないが、全文置換は既存の膨大な履歴を壊すリスクがある。
- Notion に渡す本文は**実際の改行**で組み立てる（`\n` のリテラル文字列を渡さない）。
- 日付は**JST**。`git log` の `%ad` は環境の TZ に依存するので、必要なら
  `git log --date=format-local:'%Y-%m-%d' --date=default` 等で JST 揃えを確認する
  （日跨ぎのコミットの所属日に注意）。
- commit リンクの URL は**40桁フルhash**。短縮hashだけの URL にしない。
- 既存ページに同じ変更が別表現で載っていないか、起点日の前後1〜2セクションは
  必ず読んでから書く（二重掲載の防止）。
- コミットメッセージは日本語。`Refs #` / `Closes #` の issue 参照や、
  `feat:` `fix:` などの prefix はそのまま出さず、ユーザー向け文面に翻訳する
  （コミット規約は `.claude/rules/git-workflow.md` を参照）。
- このスキルは Notion ページの追記まで。コードや他ドキュメントには触らない。
