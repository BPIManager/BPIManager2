# API v2: 全エンドポイント共通レスポンスエンベロープ

- **ステータス**: 検討中（親issue起票済み、`spec-ready`ではない）
- **対応issue**: #305

## 背景

現状、`src/pages/api/`配下の全APIエンドポイント（102ファイル、うち`v1/users/[userId]/`配下だけで約60ファイル）は共通のレスポンスラッパーを持たず、成功時のレスポンス形状がエンドポイントごとにバラバラである。

- 配列を生データのまま返す（例: [scores.ts:36](../../src/pages/api/v1/users/[userId]/scores.ts)の`return res.status(200).json(processed)`）
- 単発オブジェクトを返す（例: [apiKey.ts:26](../../src/pages/api/v1/users/[userId]/apiKey.ts)の`{ key: newKey }`、[notes/[noteId]/upvote.ts:25](../../src/pages/api/v1/users/[userId]/notes/[noteId]/upvote.ts)の`{ upvoteCount }`、[patterns/[pattern]/vote.ts:32](../../src/pages/api/v1/users/[userId]/patterns/[pattern]/vote.ts)の`{ ok: true }`）

エラー時も[withUserApiHandler.ts](../../src/middlewares/api/withUserApiHandler.ts)を経由する一部エンドポイントは`{ message: string }`で揃っているが、これを使わず素の`try-catch`を書いているファイルも多く（例: `profile.ts`）、エラーレスポンスの形も完全には統一されていない。`{ error: boolean }`のような真偽値フラグは現状どこにも存在しない。

クライアント側の[fetch.ts](../../src/utils/common/fetch.ts)（SWR共通フェッチャー）・各`src/services/swr/`のフェッチャーは、いずれも`res.json()`の結果をunwrapせずそのままSWRの`data`として返しているため、レスポンス形状の統一・非統一はそのままクライアントの型・実装のばらつきに直結している。

このような状況を踏まえ、全エンドポイントで厳密に共通の型を持つレスポンスエンベロープ（例: `{ error: boolean, errorMessage: string | null, body: any, ... }`）を導入し、`/api/v2/`として展開する案が挙がった。

## 移行方式として検討した選択肢

エンベロープ導入自体の是非とは別に、導入する場合の移行方式は以下の4案が考えられる。

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A: 一括移行（flag day） | `/api/v1/`を`/api/v2/`へ即座に全面置換し、旧形状は廃止する | 移行期間中の二重管理が発生しない。エンドポイント・クライアントの形状が常に一致する | 102ファイル＋対応する全SWRフェッチャー・呼び出し側を同時に書き換える必要があり、1PRで検証しきるにはリスクが大きすぎる。ロールバックも困難 |
| B: エンドポイント丸ごと複製し並行稼働 | `/api/v2/`を新設し`/api/v1/`と共存させるが、ハンドラの実装自体をエンドポイントごとv1・v2で複製する | 1issue=1commitの原則・`feat/`ブランチのPRレビュー運用（[issue-driven-development.md](../../.claude/rules/issue-driven-development.md)）に自然に乗る | ビジネスロジック自体はv1・v2で同一なのに実装を複製することになり、片方だけ修正されるバグ混入・保守コスト増を招く。後述の通り、現状のハンドラはビジネスロジックと`res.json()`呼び出しが分離されておらず、複製は事実上ハンドラ全体の複製になる |
| C: バージョンを分けず`v1`のまま統一 | 新バージョンを切らず、既存`v1`配下のレスポンス形状のみを段階的に統一する（[withUserApiHandler.ts](../../src/middlewares/api/withUserApiHandler.ts)の適用範囲を全エンドポイントへ拡大する形に近い） | URLパスが変わらないため呼び出し側の切り替え作業が発生しない | 「エンドポイントによって新旧形状が混在する」状態が`v1`という同一バージョン内で発生し、呼び出し側からは形状の見分けがつかない。破壊的変更であることが外部から見えにくく、事故りやすい |
| D: ハンドラを「結果を返す」形に一次リファクタし、v1/v2は薄いアダプタのみ分ける | ビジネスロジックのハンドラ本体を「`res`に直接書き込む」のではなく正規化した結果（成功データ or `{status, message}`のようなエラー情報）を**返す**形に統一するリファクタを先に行い、実際に`res.status().json()`を呼ぶのはv1用アダプタ／v2用アダプタという薄いラッパー層のみにする。ハンドラ本体はv1・v2で完全に共有する | ロジックの複製が発生しない（B案の欠点を解消）。ハンドラのバグ修正はv1/v2双方に自動的に反映される。エンドポイント単位でエンドポイント（またはドメイン）ごとにsubissue分割して段階移行でき、1issue=1commitの運用にも乗る | 移行の前提として「結果を返す形」への一次リファクタが全ハンドラに対して必要（後述）。エラー種別（404・403・500等）の表現を全ハンドラで揃えた正規化された結果型に落とし込む設計が必要 |

D案はB案の代替として提案書中で追記されたもので、後述の通り実コードの調査結果に基づく。ロジック自体を変えずにエンドポイントの出力形式だけ差し替えられるかは、現状のハンドラの実装形に依存する。

### 現状のハンドラ実装：ロジックとレスポンス書き込みは分離されていない

[scores.ts:36](../../src/pages/api/v1/users/[userId]/scores.ts)の`handleGetScores`、[userId-profile.ts](../../src/lib/subhandlers/userId-profile.ts)の`handleGetProfile`/`handleCreateProfile`/`handleUpdateProfile`/`upsert`は、いずれもデータ取得・アクセス拒否判定・エラー分岐の途中で直接`res.status(...).json(...)`を呼んでいる（例: [userId-profile.ts:50-52](../../src/lib/subhandlers/userId-profile.ts#L50-L52)のアクセス拒否、[同:65](../../src/lib/subhandlers/userId-profile.ts#L65)の404、[同:94](../../src/lib/subhandlers/userId-profile.ts#L94)の成功時）。

つまり「ロジックはそのまま・出力形式だけ変える」ためには、D案のように**先に全ハンドラを「resに書き込む」から「結果を返す」形へ統一するリファクタが前提として必要**になる。このリファクタさえ済めば、v1アダプタ（現状と同じ形式で書き込む）とv2アダプタ（エンベロープに包んで書き込む）を薄く用意するだけでv1/v2の完全な論理共有・共存が可能になる。

## 未確定の論点（起票前に詰めるべき点）

- **エンベロープ型の確定**: `body`を`any`のままにするか、エンドポイントごとにジェネリクスで型付けするか（`ApiResponse<T>`のような形）。全エンドポイント「厳密に共通」という要求上、型定義自体は1箇所（例: `src/types/api.ts`）に集約する必要がある。→ 具体的なフィールド定義は#305の最初のsubissue（決定記録）で確定する
- **メタデータ欄の中身**: 「もし必要であれば認証情報など」とあるが、具体的に何を載せるか。→ [userId-profile.ts:54,67](../../src/lib/subhandlers/userId-profile.ts)で個別実装されている`viewerId`/`isSelf`を共通化対象に含める方針で仮置き（#305受け入れ基準に反映済み）
- **既存クライアントへの影響範囲**: SWRの共通フェッチャー（[fetch.ts](../../src/utils/common/fetch.ts)）をunwrap処理込みに変更する場合、全ドメインの`src/services/swr/`・`src/hooks/`が影響を受ける。D案を取る場合でも、v2移行済みエンドポイントとv1のエンドポイントを同じフェッチャーで扱えるようにするか、v2専用フェッチャーを新設するかの判断が要る（未確定、#305のクライアント移行subissueで詰める）
- **HTTPステータスコードとの役割分担**: `error: boolean`をボディに持たせる場合、HTTPステータスコード（4xx/5xx、現状193箇所で判定に使用）を引き続き正しく返すのか、常に200を返してボディのみで成否を判定する方式に寄せるのかで、エラー判定の実装コストとREST的な一貫性のトレードオフが生じる。→ 既存コードへの影響範囲を優先し、4xx/5xxを維持しつつbody側にも`error`/`errorMessage`を持たせる方式で仮置き（#305に反映済み）

## 現時点の所感（暫定、決定ではない）

エンベロープ導入自体は、現状バラバラなレスポンス形状・エラー形状を統一しSWR側の型安全性を上げる価値はあると考えられる。ただし対象が102ファイル＋全SWR消費側に及ぶため、A案（一括移行）は現実的でない。

B案（エンドポイント複製）とD案（結果返却へのリファクタ＋薄いアダプタ分離）を比べると、D案の方が明らかに筋が良い。ロジックの複製が発生せず、v1/v2間でのロジック乖離バグを構造的に防げる。issue化する場合はD案を軸に、以下の順で親issue（epic）＋subissueへ分割する方向で検討するのが妥当と思われる:

1. まず「結果を返す」正規化された結果型（成功データ／`{status, message}`等のエラー情報）を設計し、`withUserApiHandler`等の共通ミドルウェア層に組み込む（決定記録に残すべき規模の設計判断）
2. 次に既存ハンドラをこの形へ段階的にリファクタする（ロジック変更を伴わない機械的な変更のため、この段階では`fix/`や`refactor/`ブランチとして直接mergeできる可能性がある）
3. リファクタが完了したエンドポイントから、v2アダプタ（エンベロープ形式での書き込み）を追加し、対応するSWR側を段階的にv2へ切り替える

ただし上記の未確定の論点（特にエンベロープ型の確定・正規化された結果型の設計・既存クライアントへの影響範囲）は、親issue起票前に決定記録（`docs/decisions/`）として先に固めておくべき規模の判断だと考える。
