# 柔軟な外部データ取得API（GraphQL等）の導入検討

- **ステータス**: 検討中（issue未起票、`spec-ready`ではない）
- **前提**: [docs/decisions/0009-api-v2-common-envelope.md](../decisions/0009-api-v2-common-envelope.md)（API v2 / #305）の移行完了後に本格検討する。v2で全ハンドラが「`res`直書き」から「正規化結果（`HandlerResult<T>`）を返す純粋関数」へ移行するため、それが本提案のどの案でもリゾルバ層の下地になる
- **関連**: 既存の外部アクセス面 = MCPツール（`src/lib/mcp/tools/`）+ OAuth + `apiKey`認証

## 背景 / 動機

`src/pages/api/` のエンドポイントは102本あり、特に `src/pages/api/v1/users/[userId]/stats/` だけで約17本ある。数が多い理由自体は「SWRで画面パーツ単位に個別キャッシュ・個別revalidateする」という現行フロントの作りの必然の結果であり、内部利用としては妥当。

一方で、**third-party（外部開発者・APIキー利用者）に対して「必要なデータを必要な形で柔軟に取得させたい」** という要求がある。エンドポイントを1本ずつ追加していく方式ではこの要求に応えにくく、GraphQL的な単一エンドポイントを入れられないかという発想が出発点。

## 何が課題か（GraphQLを素朴に入れると重い理由）

サーバ導入自体（`graphql-yoga` を1ルート）は軽い。効いてくるのは以下。

### 1. 認可モデルがルート単位からグラフ横断単位へ変わる

現行は `withUserApiHandler` が **ルートの入口で1回** `checkUserAccess(req, userId)` する「門番1人」モデル。GraphQLは1クエリが `user(id) → follows → follows.scores → rivals → rivals.scores` のようにグラフを横断できるため、**横断経路のどこで他人のデータに到達してもその都度チェックが要る**。

BPIMには非公開プレイヤー・フォロー限定公開・フォローリクエスト・ブロック相当の関係があり、これらの可視性判定は現状 `src/lib/subhandlers/` や各エンドポイントに分散している。GraphQL化では「リゾルバ単位の default-deny 認可」＋「可視性判定を単一レイヤに集約し全リゾルバで再利用」が必須。チェック漏れが即データリークになり、グラフ構造上そのエッジは増える。

### 2. 公開エンドポイント特有の宿題

| 項目 | 内容 |
|---|---|
| introspection | 公開するとスキーマ全体が見える。internal型を隠すか、公開用スキーマを別途curateする |
| クエリコスト / DoS | `follows { follows { follows { scores } } }` を誰でも投げられる。深さ制限・複雑度（コスト）制限・ページネーション強制・APIキー単位レート制限が必須 |
| N+1増幅 | DataLoader無しだと1クエリが数千DBクエリに化ける。公開だと可用性リスク。現行RESTは各エンドポイントが自前でbatchクエリしておりN+1が無い |
| CDNキャッシュ | 公開RESTはCDN前段に置けるが、GraphQL POSTは置けない。persisted queryが要る |
| 破壊的変更 | third-partyがスキーマに依存するとフィールド削除が破壊的。deprecation運用の規律が要る |
| クライアント移行 | 内部フロントも合わせるなら SWR → Apollo/urql。`src/hooks/` 22ドメイン・112ファイル、`useSWR` 25箇所、および正規化キャッシュ・楽観更新コードの書き直し |

規模感は「#305のスコープ × 2〜3、かつ一方通行の扉」。

## 検討する選択肢

| 案 | 概要 | 長所 | 短所 |
|---|---|---|---|
| A: フルGraphQL（内部フロントも移行） | `db.ts`ベースに近い広いスキーマを公開し、SWRもApollo/urqlへ全面移行 | 内外で1つのデータ層。フロントが必要フィールドだけ取れる | 上記コストが最大。認可・DoS・キャッシュ・クライアント移行すべてを同時に負う。ロールバック困難 |
| B: curateした read-only 公開GraphQL（内部フロントはSWR維持） | 公開曲・公開ランキング・APIキー本人のデータ等、**安全に出せる型だけ**を持つ別スキーマを公開。任意ユーザー横断は出さない。内部フロントは現行REST/SWRのまま | blast radiusが小さい。可視性判定を1レイヤに閉じ込めやすい。段階導入可 | GraphQLの旨味（任意の柔軟性）は限定的。スキーマを人手でcurate・保守するコスト |
| C: REST + sparse fieldsets / include | 既存RESTに `?fields=` `?include=` を足し、`stats`等は `/api/v2/users/[id]/stats?metrics=radar,activity` の1本へ集約。SWRキーは`metrics`ごとに分けキャッシュ維持 | 認可はルート単位のまま。移行コスト最小。`stats`本数問題は直接解消 | 「任意のグラフ構造で取る」までは行かない。柔軟性は中程度 |
| D: tRPC | Next同一リポジトリでプロシージャ定義、エンドポイント実質1本、e2e型 | TS縛りでよければ内部利用の費用対効果は良い | 外部公開（OAuth/apiKey/MCP）とは相性が悪く二重管理。third-party向けの「柔軟な公開API」という当初動機には応えない |
| E: MCPツール面の拡張 | 既存の `src/lib/mcp/tools/` + OAuth + apiKey（既に「外部コンシューマがプライバシーを尊重して他人データを取る」を解いている）を拡張し、取得軸・粒度を増やす | ゼロから作らない。認可の前例（`src/lib/mcp/auth.ts`・`getUserScores.ts`の可視性チェック）を再利用 | ツール単位の追加になり「任意フィールド選択」の柔軟性は出ない。MCPクライアント前提 |

## 現時点の所感（暫定、決定ではない）

- 当初動機（third-partyへの柔軟な公開アクセス）に対し、A案は費用対効果とリスクが見合わない。
- **B案（curate公開GraphQL）または C案（sparse fieldsets）を軸**に検討するのが妥当。`stats`の本数という具体的な痛みだけならC案で足りる。「外部が任意の形で取れる」を本気で狙うならB案。
- いずれの案でも #305（v2 = ハンドラの純粋関数化）が下地になるため、**まずv2を完了させ、その上で本提案を再評価する**。
- 次アクション: 要件を詰める（誰が / 何のデータを / どの粒度・どの認可境界で取れると嬉しいのか。想定するthird-partyユースケースの具体例。レート制限・課金の想定）。要件が固まったらB/Cを軸に決定記録へ落とす。

## 対応範囲外（現時点）

- 具体的なスキーマ設計・ライブラリ選定
- 内部フロント（SWR）の移行可否
- 既存 `/api/v1`・MCPツールの扱い（存続 / 統合）
